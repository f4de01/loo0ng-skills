## Notes

- 每个会话先读 `CONTEXT.md`、`docs/adr/`、`AGENTS.md`（两条硬边界、五条结构不变量）。
- **先量不先改**对整个 A 股有效：拿到一条稳定复现的反馈回路（一条命令跑一次就看见慢）之前不许猜原因，测量之前不改任何代码。性能与行为分开改，混在一起改会让 eval 红了说不清是哪一边。
- 环境是一张四格矩阵（mac / Windows 乘 WPS / Word），主力格 mac + WPS 没有渲染后端；随 skill 包分发的脚本按 python 3.9 写，`tests/`、`evals/`、`scripts/` 是开发侧不受此限。
- 增、删、改名任一 skill 都走 `.agents/registration.md` 的登记八步（双旗、生成器、三份清单、README、路由入口表、relink、changeset、三条校验），删一件同样走一遍。
- 每张 skill 票的完成定义是「在真实案件会话里被真实触发过一次」，两平台都实测通过，以 Codex 办案会话为准。
- 认领人固定 f4de01；子票以 GitHub sub-issue 挂在本图下，阻塞用原生 issue dependencies。
- 0.3.0 收口时结算走 `.github/workflows/release.yml`，先干跑一次读 job summary。

## 可以现在开的票

按依赖顺序，类型按 wayfinder 四类。

### A 股　出一版为什么慢、七件该怎么修剪

1. **出一版的时间都花在哪**（task，前沿，无阻塞）
   在开发机上建那条反馈回路，按上面五段分别计时，量出「多慢、哪一段、什么规模、是不是每次」。律师那台机上的一次量由交付那张票带回（他那边没有渲染层，两组数放在一起才看得出哪一段是本机特有的）。这张票的交付物是数，不是优化点。
2. **七件 skill 的清单该不该动**（grilling，弱依赖 1）
   哪几件该合、哪件该拆、有没有该死的、要新增哪几件；ADR-0009 当年定八件时的判据是什么，还成立吗；`loo0ng-doit` 那 20 KB 是清单问题还是正文问题。
3. **正文修剪的判据**（grilling，被 1、2 阻塞）
   剪什么、什么不许剪（封条那条风险）、哪些该外移到同级参考文件、model-invoked 的 description 四要素与 1,024 字上限不变。修剪要不要与性能修复合成一张实现票，在这里裁。

### B 股　可视化插件

> 2026-09-16 附注（ADR-0029）：4、5、6 三题已裁，不必再开票。宿主定为原版 Zebar 加一个自有组件包，首版只读进度、提醒整块后移，案件靠扫律师指定的根目录发现，接口用现有 `图视图.json` 原样不升版，不新增 skill 也不并进 `ask-loo0ng`。7 变形为新建 public 仓库 `loo0ng-widget` 的第一个分支，不回本仓库开 `prototype/` 分支。术语随之改：「可视化插件」改称「桌面卡片」。

4. **插件的宿主与呈现形态**（research，前沿，无阻塞）
   官方 MCP App、独立 app、落盘 HTML 三条各自的代价，先重核「两个 CLI 都还不渲染」这条事实。`docs/3.0-handoff.md` 第 7 节当年把形态列为第一道决策题，制图时改判为「接口先于形态可定」，接口已定，现在轮到形态。
5. **插件读什么，谁给它**（grilling，被 4 阻塞）
   ADR-0011 定的 `图视图.json` 够不够画；不够时补的是引擎还是插件自己算；多案件把几份读在一起是不是本图的事（map #1 把它划给了这张图）。
6. **接通插件的那件 skill 存不存在**（grilling，被 4、5 阻塞）
   律师要看图时打的那一句落在哪儿：新增一件 skill、并进 `ask-loo0ng`、还是插件自己的事不需要 skill。ADR-0011 关掉「图存档」槽的理由要在这里被正面回答，别默默推翻。
7. **插件本体**（prototype，被 4、5 阻塞）
   用合成领域「菜园」与几个不同状态的种子，把一张真图画出来看看。throwaway 的规矩照 prototype：答的是设计题，留在 `prototype/` 分支上作 primary source。

### C 股　泛化

8. **泛化到所有领域还差什么**（task，前沿，无阻塞）
   三件需求的第三件。0.2.0 之后逐条核：新领域从空图起手、两侧同一条路、入库、逐节点回流，哪些已经够，哪些只差一次真实实跑，哪些真的还缺机制。先核再开票，别先假定缺口。
